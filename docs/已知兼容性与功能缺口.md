# 已知兼容性与功能缺口

> 记录运行期在账本（`request_logs`）中观察到、但**不在当前设计范围内**的上游兼容性与端点缺口。
> 供后续决定「补功能 / 转上游 / 仅记录」时对齐；不改变现有透传与归因契约。
> 更新日期：2026-09-21。

## 1. ~~`/v1/messages/count_tokens` 未实现~~ —— 已实现（2026-09-21）

**现象**（修复前）：Anthropic 客户端在正式请求前调用 token 计数端点，网关未注册该路径，落到兜底 404。

- 请求：`POST /v1/messages/count_tokens`
- 落库：`error_domain = client`、`error_kind = unknown_endpoint`、HTTP 404
- 观测：释放库（`%APPDATA%\com.apnea.lumen\lumen.db`）截至 2026-09-18 累计 **1113 次**，是账本里最高频的错误类目

**原因**：`gateway/handlers.rs` 只为 `/v1/messages` 注册了 handler（`MESSAGES_ENDPOINT`），未覆盖 Anthropic 规范中的 `/v1/messages/count_tokens`；未匹配路径统一走 `not_found` 兜底并落一条 `unknown_endpoint` 流水。

**处理**：注册该端点（含无版本别名 `/messages/count_tokens`），复用 `gateway/estimate.rs` 的 tokenizer **本地估算**返回 `{"input_tokens": n}`——不走上游、不计费、且**不落账本**（它不是生成调用，记进去只会搅浑调用次数）。别名解析失败仍返回 `model_not_found`。

## 2. 跨协议转换拒绝 `messages[].role = "system"`

**现象**：Anthropic 入站请求在 provider 无 `anthropic` 端点、回退到 `openai`（Chat）端点做协议转换时，整条请求在**到达上游之前**失败。

- 请求：`POST /v1/messages`（`stream: true`）
- 落库：`error_domain = gateway`、`error_kind = conversion_failed`、`http_status = NULL`（未发出上游请求）
- 错误文案：`协议转换失败：unsupported: messages role system`
- 观测：`gpt-6-astra` 别名（provider `OpenAI` / `micuapi.ai`，仅挂 `openai` + `responses` 端点），2026-09-17 4 次

**原因**：`llmwire` 的 Messages 解码只接受 `user` / `assistant` 两种角色（`src/codec/messages/mod.rs:199-204`），`messages[]` 内出现 `role: "system"` 即返回 `unsupported`。Anthropic 规范要求 system 放顶层 `system` 字段，但部分客户端把它作为一条 message 混在 `messages[]` 里。

**影响**：凡「Anthropic 入站 + 上游只有 `openai` / `responses` 端点」的组合，只要请求体含 system-role message 就会整单失败——不是降级，是转换核直接报错；且因 `conversion_failed` 不产生上游请求，客户端看到的是网关错误而非上游错误，归因落在 `gateway`。

**可选处理**：

1. 为该 provider 补一个 `anthropic` 端点 → 同协议透传，绕开转换；
2. 在 `llmwire` 侧把 `messages[].role = "system"` 提升为顶层 `system`（SDK 变更，需与上游仓库协调）；
3. Lumen 侧预规范化——涉及「同协议透传 vs 替客户端兜底」的边界取舍，暂不做。

> 决策：待定，当前仅记录。

## 3. 客户端未携带会话头时，OpenCode Go 返回 400

**现象**：OpenCode Go 对缺失 `x-opencode-session` 的请求返回 400（`upstream_rejected`，文案 `Request is missing x-opencode-session...`）。账本 2026-09-14 ~ 09-21 累计 27 次，且这些请求的 `session_id` 全部为 `NULL`。

**原因**：该头由客户端提供。Lumen 侧已用 provider 的 `replace` 头映射把 `x-claude-code-session-id` 改写成 `x-opencode-session`（配置在「上游提供商 → 请求头映射」），但**同一个客户端有时并不发这个头**——此时映射无源可映射，网关也补不上。

**影响**：请求在到达上游前就被拒（4xx 不触发降级，直接透传），客户端看到的是上游的 400 而非网关错误。

**决策**（2026-09-21）：**网关不合成会话值**。

- 会话头的价值在于**会话级稳定**（同一会话每次用同一个值，prompt cache 才命中）。由网关编一个——无论随机还是哈希——都是越权；用固定常量更糟：所有会话挤进同一条 cache 分片，省了报错却多花钱。
- 客户端不发就是没有，网关**只做映射**。这与 `2026-09-12-session-dimension-and-header-mapping.md` 的既定决议一致（「会话解析 = 捕获，不合成；`fallback=generate` 留待后续」）。
- 可诊断性已补：候选为空时网关会点名「哪一关卡住了目标」，401/400 缺头类错误也能从 `error_kind` 直接分辨。

> 若要真正解决，得由客户端稳定地发会话头；网关侧不做兜底。
