# 网关请求头行为

Lumen 是本地 LLM 网关：客户端（OpenCode / Codex / Claude Code 等）把请求发到 Lumen，Lumen 再转发给上游提供商。本说明澄清**上游最终会收到哪些请求头**，以及如何用提供商上的「请求头映射」控制它。

## 一、配置轴：挂在提供商，不挂在模型

请求头是**协议 / 提供商**的属性，不是模型的属性。因此映射配置在**上游提供商**上，同一 provider 下的所有模型共用一份，路由 / 模型层没有请求头配置。

## 二、四意图

| 意图 | 字段 | 语义 |
|---|---|---|
| 添加 | `extraHeaders` | 常量 `name: value`，永远发出 / 覆盖 |
| 透传 | `headerRules.forward` | 放行客户端头（支持 `*` 通配） |
| 替换 | `headerRules.replace` | 把客户端头 `from` 以 `to` 的名字发出 |
| 移除 | `headerRules.remove` | 从最终结果中删除（支持 `*` 通配，优先级最高） |

**透传不限定 `x-` 前缀**：像 Codex 的 `session_id`、`x-codex-turn-metadata` 这类非 `x-` 前缀 / 含下划线的原生头都能放行（字符集按 RFC 7230 的 header token）。这是刻意的——曾有网关工具只放行 `x-*`，导致这类头无法透传。

替换规则写作 `来源 → 目标`，兼容 `->` / `=>`。替换**不改变来源头本身是否发送**（它是否发送由底座或透传决定）。

## 三、默认底座（开箱即"像直连"）

不配置任何规则时，网关默认放行一批安全头，避免用户为常见头逐个配置：

```
user-agent, accept-language, traceparent, tracestate,
anthropic-version, anthropic-beta,
openai-beta, openai-organization, openai-project
```

底座是可扩展的白名单；用 `remove` 可以否决其中任何一项。

## 四、求值顺序（固定）

```
内置底座
  → 透传   (forward)
  → 替换   (replace)
  → 添加   (extraHeaders)
  → 移除   (remove)        ← 最高优先级，deny wins
  → 硬黑名单               ← 无条件剥离
  → 鉴权                   ← 最后注入，规则无法覆盖
  → anthropic-version 兜底
```

因为顺序固定：`extraHeaders` 覆盖前序同名头；`remove` 能删掉底座 / 透传 / 添加产出的任何头；`replace` 写到某个头名时覆盖该名既有值。

## 五、不可配置的保护

- **硬黑名单**（任何规则都无法让它们出现）：`host`、`content-length`、`connection`、`transfer-encoding`、`authorization`、`x-api-key`、`x-goog-api-key`。
- **鉴权最后注入且无条件覆盖**：`bearer` / `x-api-key` / `x-goog-api-key` 由 Lumen 按提供商配置写入。因此规则永远无法伪造鉴权，**下游虚拟密钥绝不泄漏给上游**。
- 保存提供商时按同一套规则校验（`validate_provider_header_rules`），非法规则（空名 / 非法字符 / 命中受保护头 / 替换目标带通配）直接拒绝。

## 六、会话头：要的是「稳定」，不是「格式」

OpenCode Go / Zen 用 `x-opencode-session` 做**粘性路由与 prompt cache 分片**。官方要求是：

> Send a **stable** session ID in `x-opencode-session` for each conversation.

关键结论（2026-09 调研）：

- **不校验 `ses_` 形状**：社区实现直接透传 `x-session-affinity` / `x-session-id` 的值，甚至用 UUID，不做前缀归一化。值是不透明的。
- **要的是稳定性**：随机 / 每请求变化的会话值会让请求反复落到同一（可能损坏的）副本，比不带还糟（见 `anomalyco/opencode#46011`）。因此**绝不要在网关侧每请求生成新值**。
- Go 目前认识 Codex / Claude Code 的原生会话头，但**不保证长期兼容**，且"代理场景下仍可能缺失，转发时要保留会话头"。

因此推荐做法是**替换**，把客户端已有的稳定会话头改名送给上游：

| 客户端 | 客户端头 | 替换规则 |
|---|---|---|
| Codex | `session_id` | `session_id → x-opencode-session` |
| Claude Code | `x-claude-code-session-id` | `x-claude-code-session-id → x-opencode-session` |
| OpenCode（第三方 provider） | `x-session-affinity` | `x-session-affinity → x-opencode-session` |

同一 provider 可能被多个客户端使用，可同时配置多条替换规则（按顺序，后写覆盖先写）。

## 七、配方示例

**OpenCode Go（被 Codex 使用）**

- 透传：留空（底座已含常见头）
- 替换：`session_id → x-opencode-session`
- 添加：`user-agent: opencode/local`（可选，视上游要求）
- 移除：留空

**转发 Anthropic beta（Claude Code → Anthropic）**

- 透传：留空（底座已含 `anthropic-beta` / `anthropic-version`）；如需其它头再补
- 替换 / 添加 / 移除：留空

## 八、与会话记账的关系

网关另有一套**会话记账**（`request_logs.session_id`）：按全局候选头名表（设置页可改）解析出会话值，仅用于日志聚合与排查，**与上游收到的头相互独立**。请求头映射只影响发给上游的头；会话记账只影响账本。二者不要混淆。
