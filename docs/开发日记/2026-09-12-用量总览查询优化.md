# 用量总览查询优化

> 日期：2026-09-12
> 提交：`3a97ed6` perf: cut usage-overview query cost and tighten the day axis
> 涉及：`src-tauri/src/db/mod.rs`、`src-tauri/src/db/stats.rs`、`src/features/usage/UsageTrendChart.tsx`、`src/features/usage/usageData.ts`

## 起因

用量页切日 / 周 / 月时有肉眼可见的卡顿。第一反应是前端——骨架屏闪烁、指标数字每次从 0 数起，看起来都像元凶。

但先量一遍，结论完全不同。

## 一、先量，别猜

**方法**：用 `inject_demo(DemoScenario::Rich)` 造一个真实磁盘库（45 天 / **59,693 行**），用 `EXPLAIN QUERY PLAN` 看执行计划，用 `Instant` 计时。

**修复前**：

| 周期 | 耗时 |
| --- | --- |
| 日 | 180 ms |
| 周 | 230 ms |
| 月 | 360 ms |

教训：**不存在「查询太复杂」，只有「执行计划选错了」。** 计划没看之前，所有优化都是猜。

## 二、三个根因

### 根因 1：索引选错，全表扫描

执行计划是：

```
SEARCH request_logs USING INDEX idx_request_logs_status (status=?)
```

`status`（成功 / 失败）只有几个取值，选择性极差，规划器却挑了这条单列索引，然后拿全部 5.9 万行逐行比 `occurred_at`。日视图真正只有 1655 行，却要扫全表。

**修复**——补复合索引：

```sql
CREATE INDEX IF NOT EXISTS idx_request_logs_status_occurred
  ON request_logs(status, occurred_at);
```

计划立刻变成：

```
SEARCH request_logs USING COVERING INDEX idx_request_logs_status_occurred
  (status=? AND occurred_at>? AND occurred_at<?)
```

覆盖索引连回表都省了。日视图 180 → 15 ms。

**关于 `SCHEMA_VERSION`**：**没有**升版本。索引是纯增量、且是 `IF NOT EXISTS`，启动时 `execute_batch(SCHEMA)` 会自动补建；升版本会触发建表重建，把现有数据冲掉。约定是「改表结构才升版本」，加索引不算。

### 根因 2：同一个周期被扫 5～8 遍

`totals` / `series` / `layers` / `model_costs` / `quality` 各是一条独立 SQL，同一时间范围反反复复扫。

**修复**——把「成功请求」的全部口径合并成**每周期一次** `(桶, 层, 模型)` 的 `GROUP BY`，从同一份结果里导出：合计、逐桶 token 累积序列、分层、分层合计、按模型花费。

时间分桶下推给 SQLite（`occurred_at` 存 UTC RFC3339，靠 `localtime` 修饰符转本地）：

| 周期 | 分桶表达式 |
| --- | --- |
| 日 | `CAST(strftime('%H', occurred_at, 'localtime') AS INTEGER)` |
| 周（周一起） | `(CAST(strftime('%w', occurred_at, 'localtime') AS INTEGER) + 6) % 7` |
| 月 | `CAST(strftime('%d', occurred_at, 'localtime') AS INTEGER) - 1` |

### 根因 3：上期在陪跑

上期数据只用于「较上期 ±%」和归因，却跟着做了完整的分桶 + 按模型分组——月视图 128 ms 全花在这里。

**修复**——上期改成只 `GROUP BY 层` 的轻查询，连 `strftime` 都不需要。

顺手删掉了前端**从未使用**的 `previous_values` 字段（Rust DTO + 前端类型 / mock / 测试一起清）。

## 三、结果

| 周期 | 修复前 | 修复后 |
| --- | --- | --- |
| 日 | 180 ms | **6 ms** |
| 周 | 230 ms | **51 ms** |
| 月 | 360 ms | **146 ms** |

月视图剩下的 146 ms 是扫 4.5 万行两次（当期 + 全记录口径的质量统计）的硬成本，属可接受范围。

## 四、决策与取舍

- **前端的「感知延迟」改成一半被否。** 试过 stale-while-revalidate（切周期保留上一份数据 + 压暗 + `aria-busy`），被否掉了：账本不能显示**错的数字**，坚持要有中间加载态。这是一次**产品语义压过性能直觉**的记录。最终前端只保留骨架，提速全靠后端。
- **感知延迟还有另一半没做**：`useAnimatedMetric` 每次目标变化都从 0 数到新值、固定 360 ms。后端快了之后，这可能是仅剩的观感成本。
- **没有把 `quality_totals` 并进 `period_stats`**：前者是全记录口径、后者是成功口径，合并能再省月视图约 19 ms，但会牺牲口径清晰度，不值。
- **日视图纵轴收紧**：`AXIS_STEPS` 细化到 `[1, 1.2, 1.5, 2, 2.5, 3, 4, 5, 6, 8]`，加 5% 顶部留白。峰值 ~2.2 时 yMax 从 5 收到 2.5，曲线不再是贴底的平线。
