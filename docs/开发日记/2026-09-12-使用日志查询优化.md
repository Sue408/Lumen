# 使用日志查询优化

> 日期：2026-09-12
> 提交：`d14437a` perf: make the log filters indexable and collapse the log page to one query、`dcacaa9` feat: fetch the log page in one round trip
> 涉及：`src-tauri/src/db/logs.rs`、`src-tauri/src/db/mod.rs`、`src-tauri/src/commands/usage.rs`、`src/features/logs/LogsPage.tsx`、`src/services/usage.ts`

## 起因

密钥页之后轮到日志页。如果说密钥页是「数据不大却莫名慢」，日志页就是明摆着的重灾区——一次进入要发 5 个查询，其中 4 个是全表 COUNT，而且 `useLiveRevision` 让**每个网关请求都重跑这一整套**。

## 一、先量

演示数据 59,693 行真实磁盘库，`EXPLAIN QUERY PLAN` + `Instant` 计时。

| 查询 | 耗时 | 计划 |
| --- | --- | --- |
| `list` 待处理（limit 100） | 5 ms | 走时间索引 |
| `count` 待处理 | 32 ms | SCAN 全表 |
| `count` 全部（摘要） | 23 ms | 全索引扫描 |
| `count` 失败（摘要） | 28 ms | 全表 |
| `count` 存疑（摘要） | 30 ms | 全表 |

单次加载约 **118 ms**，还叠着 5 次 IPC 和 5 次锁。

## 二、根因

### 根因 1：`?N IS NULL OR col = ?N` 让一切无法索引

原来的 `FILTER_WHERE` 是这么写的：

```sql
WHERE (?1 IS NULL OR route_alias = ?1)
  AND (?2 IS NULL OR status = ?2)
  ...
```

规划器在准备语句时看不到参数的**实际取值**，于是没法把这些 `OR` 折叠成索引查找——**哪怕一个过滤条件都没传，COUNT 也是全表扫描**。`count all` 的 23 ms 就是这么来的。

### 根因 2：摘要用三条独立 COUNT

总 / 失败 / 存疑各扫一遍全表，三遍 81 ms。

### 根因 3：五条查询各自一次 IPC、一次锁

list、count、摘要三条，全部串行在同一个 `Mutex<Connection>` 上。

## 三、修法

1. **动态拼 WHERE**（`build_where`）：只把**激活的**条件拼进 SQL、绑真实值；list 与 count 共用同一个 builder，不再靠人工保持同步。无过滤的 COUNT 由此命中 SQLite 快路径，有过滤的按列走对应索引。
2. **摘要保持三条索引 COUNT**（见下，合并方案被否）。
3. **一条命令**（`query_log_page_cmd`）一次返回 `{ logs, total, summary }`，5 次 IPC → 1 次。

## 四、一个被数据推翻的方案

原计划把摘要「合并成一条 SQL 一次扫完」：

```sql
SELECT COUNT(*), SUM(status='error'), SUM(usage_source IN ('missing','partial')) FROM request_logs
```

实测 **31 ms** —— 比三条索引 COUNT 加起来还慢。真正的原因是 `usage_source` **没有索引**：只要不索引，无论如何写法都得全表扫。

所以方案改成**加 `idx_request_logs_usage_source`，摘要保留三条 COUNT**：

| 查询 | 之前 | 之后 |
| --- | --- | --- |
| `COUNT(*)` 无过滤（快路径） | 23 ms | 1.2 ms |
| `COUNT status='error'` | 28 ms | 0.27 ms |
| `COUNT usage_source IN (...)` | 30 ms | 0.46 ms |
| `COUNT` 待处理的 `OR`（MULTI-INDEX OR） | 32 ms | 1.3 ms |

**教训：先量再定形。** 「合并查询」听起来总是更优，但这里真正的瓶颈是缺索引，合并反而把三条能走覆盖索引的查询变成一条全表扫描。

## 五、修 A 撞出来的回归，修 B 补上

谓词一旦可索引，`list` 出了新问题：规划器为「待处理」的 `OR` 选了 **MULTI-INDEX OR**，代价是**丢掉时间序、被迫排序**——而列表本来就是「按时间倒序、够数即停」，早停一没，4 ms 变 24 ms。

修法：对「待处理 / 用量存疑」这两类 `OR`・`IN` 谓词的列表**显式钉在时间索引上**：

```sql
SELECT * FROM request_logs INDEXED BY idx_request_logs_occurred ... ORDER BY occurred_at DESC LIMIT ?
```

→ 1.6 ms。`status`、别名、时间范围这些仍交给规划器挑最优索引（`status` 会用 `(status, occurred_at)` 复合索引，比硬钉时间索引更优）。

这里有意做了**局部**而非全局的强制：`INDEXED BY` 是硬提示，全局使用会在「高选择性过滤 + 老数据」下反噬，只对确定会踩 MULTI-INDEX OR 的两类谓词使用。

## 六、结果

| 查询 | 之前 | 之后 |
| --- | --- | --- |
| `list` 待处理 | ~5 ms | ~4 ms |
| `count` 待处理 | 32 ms | 1.3 ms |
| `count` 全部 | 23 ms | 1.2 ms |
| `count` 失败 | 28 ms | 0.27 ms |
| `count` 存疑 | 30 ms | 0.46 ms |
| **合计** | **~118 ms / 5 次 IPC** | **~7 ms / 1 次 IPC** |

约 15 倍。索引同样以增量方式加入 `SCHEMA`（`IF NOT EXISTS`），**不升 `SCHEMA_VERSION`**，避免已有数据被重建清空。

## 七、遗留

- **live 刷新未处理**：`useLiveRevision` 仍让每个网关请求重跑整套，只是成本从 ~118 ms 降到 ~7 ms。若还要压，可只在第一页刷新或延长去抖。
- `list_log_aliases` 仍单独一次查询（仅挂载时）。
- `docs/UIUX设计文档` 里日志页「过滤下推后端」的描述依旧成立；本次是把下推做对了，而非改语义。
