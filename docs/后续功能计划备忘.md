# 后续功能计划备忘（非 MVP）

> 记录 Lumen 在 MVP 之后的方向与已达成的一致决定，供接续时对齐。
> 更新日期：2026-09-11。
> 本文替代此前的《模型路由与提供商的代码逻辑优化意见》与《Lumen 界面设计优化建议》两份意见稿（相关项已跟进，原文已删除）。

## 1. 范围决定

MVP 以「路由模型 ↔ 上游模型一一对应」为主：一条路由实际取首个 `enabled` 目标（`gateway/resolve.rs`）。多目标配置是有序降级链的**地基**，保留但暂不生效。

以下均为**后续功能（非 MVP）**：

1. 完整 IR 协议转换（接入 `llm-protocol` SDK，见 `docs/llm-protocol对接需求.md`）。
2. 真实降级策略（失败切换）。
3. 路由级能力 / 上下文底线。

## 2. 已就位的地基

- 路由协议创建后锁定，且所有目标必须与路由协议一致（`db/routes.rs`）。
- 目标按 `priority` 有序、`enabled` 可过滤。
- 每一跳的规范用量、缓存边界与计费口径已统一（`gateway/usage.rs`）。

## 3. 降级策略：需先拍板的语义

1. **触发条件**：只对连接失败 / 超时 / 5xx / 429 降级；4xx、鉴权失败、内容策略**不**降级（换上游无意义且重复计费）。
2. **流式提交点**：向客户端发出首字节后不可再切上游。降级只可能发生在「建连 + 首块到达之前」；否则明确声明「开流后不降级」。
3. **按 attempt 记账**：失败的上游尝试也必须进账（否则账单低报 —— 而「账准」是产品存在的理由）。优先级高于能力底线。至少每次尝试一条记录，或记录 `attempt_index` 与实际履约 target。

## 4. 能力 / 上下文底线：建议建模为「降级候选的运行时筛选」

- 路由声明 `capabilities` / `context_window` 作为**下限**。
- **筛选而非硬校验**：`resolve` 返回有序候选后，跳过不满足底线的目标；保存期最多**告警**（「没有备用满足底线，降级将不可用」），不硬拒。这样「强主模型 + 弱备用」仍可配，而契约不被破坏。
- 与协议规则**解耦**实现，未来接入 IR 转换时可只摘掉协议那一条。

## 5. 落地顺序（未来）

1. 收敛能力词表（后端 const 为权威、前端镜像；当前仅前端 `providerModel.ts`）。
2. `resolve` 由 `LIMIT 1` 改为有序候选 + `forward` 尝试循环 + **按 attempt 记账**。
3. 非流式降级先跑通（可测、安全）。
4. 流式：pre-first-byte 降级，或明确不降级。
5. 能力 / 上下文候选筛选（soft）。

## 6. 相关技术债 / 前置

- 能力词表后端无约束（`Vec<String>`）。
- `save_route` 全量重建目标（`route_targets.id` 每次变化）；未来若日志需要引用 target，应改为按 `(route_id, upstream_model_id)` upsert。
- `docs/后端接口文档.md` 需随上述变更持续同步。
