## 3. 路由调用策略（「降级」只是其中一环）

> 「降级」只描述失败后的行为。完整策略 = **①候选过滤 + ②选择策略 + ③失败策略 + ④记账**，四者正交。
> 决议（2026-09-12）：选择策略**只保留优先级**，默认**粘性**；轮询 / 加权 / 延迟优先 / 对冲不做。

### 3.1 选择策略：只保留优先级（稳定主目标）

- 单用户产品**没有并发负载可分摊**，轮询 / 加权解决的是不存在的问题。
- 主动轮换会**破坏 prompt cache**：Anthropic 写入 ≈ 1.25×、读取 ≈ 0.1×；OpenAI 读取 0.5×；缓存作用域为**账号级**（换 key 也会 miss）。主动轮换 = 每次多付一次写入、丢掉读取折扣，直接多花钱。
- 因此默认**粘性**：只要主目标可用就不换；**降级是例外，不是常态**。
- **UI 一致**：路由目标列表的上下顺序**本身就是优先级**，移除行间 `↓` 连接符（`RoutingPage.tsx` / `config.css` 的 `.target-connector`）——它把「兜底路径」误画成「默认路径」，而顺序已由 `target-rank` + `target-role` 表达，去掉后语义更通用。

### 3.2 失败策略

1. **触发条件**：只对连接失败 / 超时 / 5xx / 429 降级；4xx（429 除外）、鉴权失败、内容策略**不**降级（换上游无意义且重复计费）。
2. **429 分类**：429 被重载，需先分「短时限流」与「额度耗尽」。有短 `Retry-After`（等待上限取 **10s**）→ **等一次、重试同一目标**（保 cache）；额度类错误 / 长冷却 / 无可用信号 → **降级切下一个**。
3. **冷却**：每个目标一个 `cooldown_until` 时间戳，**内存态**（重启清空，可接受）、**带过期**；触发切换前标记冷却（429 记 300s、其余 60s），冷却中的目标在候选过滤阶段跳过。
4. **流式提交点**：向客户端发出首字节后不可再切上游。降级只可能发生在「建连 + 首块到达之前」；否则明确声明「开流后不降级」。

### 3.3 按 attempt 记账

失败的上游尝试也必须进账（否则账单低报 —— 而「账准」是产品存在的理由）。优先级高于一切可选功能。每次尝试至少一条记录，带 `attempt_index` 与实际履约 target。

### 3.4 主动预算（**非目标**，且不参与路由）

仅对**透明按量计费**的 key 做预算预警。订阅多为不透明 / 半透明计费（额度是厂商私有单位、上游不返回花费），「主动算比例」不现实；路由触发以**反应式 429** 为准。

> 决策（2026-09-12）：**非目标，不做**。预算以反应式 429 为准（M2 已实现 429 分类与冷却）。本节仅存档建模。

## 4. 能力 / 上下文底线：建议建模为「降级候选的运行时筛选」

- 路由声明 `capabilities` / `context_window` 作为**下限**。
- **筛选而非硬校验**：`resolve` 返回有序候选后，跳过不满足底线的目标；保存期最多**告警**（「没有备用满足底线，降级将不可用」），不硬拒。这样「强主模型 + 弱备用」仍可配，而契约不被破坏。
- 与协议规则**解耦**实现，未来接入 IR 转换时可只摘掉协议那一条。

> 决策（2026-09-12）：**非目标，不实现软筛选**，只统一能力词表（M1.3 已完成）；本节仅存档建模。

## 7. 开发期数据策略：Schema 变更即重建空库（已废弃）

- 旧做法：`SCHEMA_VERSION` 不符时 `reset()`，`DROP_ALL` 包含 `request_logs` 与 `settings`——任何表结构改动都会清空全部流水与设置。
- 这是**发布前的有意识妥协**：字段与结构尚未定型，逐列迁移成本高、收益为零，且当时数据均为测试数据。
- 收口（2026-09-12，**已落地**）：增量迁移框架随 M1.1 完成（`db/migrations.rs`）。此后表结构变更一律走迁移阶梯，`request_logs` 与 `settings` 不得再随版本升级丢失；`v > 最新` 拒绝启动而非静默清库。

## 8. 性能优化方向（待基准验证，尚未实施）

背景：`request_logs` 的查询维度（时间 / virtual_key / 层 / status）已由覆盖索引承担，且 `with_db` 单连接串行。**拆事实表在当前负载下收益有限、反而增加写入成本**，不作为首选。按性价比排序：

1. **写入热路径**：每请求 1 次 INSERT + 1 次额度 SUM。可评估 `PRAGMA synchronous=NORMAL`（WAL 下安全）省 fsync；审视索引写放大（`idx_request_logs_alias`、`idx_request_logs_usage_source` 是否必要）。
2. **让规划器自选索引**：日志列表现用 `INDEXED BY` 硬钉 occurred 索引（`db/logs.rs`）。批量写入后跑 `ANALYZE` / `PRAGMA optimize`，可能让多数 hint 可撤。
3. **统计提速**：总览页真变慢时，加按 `(day, virtual_key_id, upstream_model_name)` 的 rollup 表（插入时增量 upsert），把总览从扫明细变成读几十行。代价是写入复杂度与跨期翻转的一致性。
4. **并行读取**：若要实现「多维度并行查询」，唯一有效手段是 WAL + 读连接池（多读连接），而非拆表；需处理 `SQLITE_BUSY`。
5. **不采用**：按月水平分表（跨期需 UNION、全局搜索要改造，15 万行/年远未到量级）；星型规范化（破坏账本的点时快照语义）。

**验证方式**：先跑现有基准 `bench_overview` / `bench_logs` / `bench_key_usage`（`#[ignore]`，`DemoScenario::Rich` 造 >2 万行），记录耗时与 `EXPLAIN QUERY PLAN`；再用 50 万 / 100 万行复跑看拐点，据此决定是否实施 3 / 4。

**基线快照（2026-09-12，debug 构建，`DemoScenario::Rich` = 59,693 行）**：基准依赖 `db::demo`，而该模块被 `#[cfg(debug_assertions)]` 门控，故只能在 debug 下跑（release 下编不过）。

| 查询 | 耗时 | 计划 |
|---|---|---|
| 总览 Day / Week / Month | 7–10 / 49–72 / **137–145** ms | 覆盖索引 `idx_request_logs_status_occurred` |
| 密钥额度（5 keys） | 2.7–2.9 ms | 覆盖索引 `idx_request_logs_key_status_occurred` |
| 日志 attention 列表（limit 100） | 5.1 ms | `INDEXED BY` 硬钉（planner 自选 16.8 ms，已否决） |
| 日志 count all / failed / unreliable | 0.17–1.3 ms | 覆盖索引 |
| `list_aliases` | 5.7 ms | — |

结论：60k 行下除 **Month 总览（~140ms）** 外都在 10ms 量级；Month 是唯一潜在痛点，但尚未到「必须优化」。rollup / 读连接池维持 §5.5 按需状态。
