# 后续功能计划备忘（非 MVP）

> 记录 Lumen 在 MVP 之后的方向与已达成的一致决定，供接续时对齐。
> 更新日期：2026-09-12。
> 本文替代此前的《模型路由与提供商的代码逻辑优化意见》与《Lumen 界面设计优化建议》两份意见稿（相关项已跟进，原文已删除）。

## 1. 范围决定

MVP 以「路由模型 ↔ 上游模型一一对应」为主：一条路由实际取首个 `enabled` 目标（`gateway/resolve.rs`）。多目标配置是有序降级链的**地基**，保留但暂不生效。

以下均为**后续功能（非 MVP）**：

1. 完整 IR 协议转换（接入 `llm-protocol` SDK，见 `docs/llm-protocol对接需求.md`）。
2. 真实降级策略（失败切换）。
3. 路由级能力 / 上下文底线。

## 2. 已就位的地基

- 路由协议创建后锁定，且所有目标必须与路由协议一致（`db/routes.rs`）。
- 目标按 `priority` 有序、`enabled` 可过滤。
- 每一跳的规范用量、缓存边界与计费口径已统一（`gateway/usage.rs`）。

## 3. 降级策略：需先拍板的语义

1. **触发条件**：只对连接失败 / 超时 / 5xx / 429 降级；4xx、鉴权失败、内容策略**不**降级（换上游无意义且重复计费）。
2. **流式提交点**：向客户端发出首字节后不可再切上游。降级只可能发生在「建连 + 首块到达之前」；否则明确声明「开流后不降级」。
3. **按 attempt 记账**：失败的上游尝试也必须进账（否则账单低报 —— 而「账准」是产品存在的理由）。优先级高于能力底线。至少每次尝试一条记录，或记录 `attempt_index` 与实际履约 target。

## 4. 能力 / 上下文底线：建议建模为「降级候选的运行时筛选」

- 路由声明 `capabilities` / `context_window` 作为**下限**。
- **筛选而非硬校验**：`resolve` 返回有序候选后，跳过不满足底线的目标；保存期最多**告警**（「没有备用满足底线，降级将不可用」），不硬拒。这样「强主模型 + 弱备用」仍可配，而契约不被破坏。
- 与协议规则**解耦**实现，未来接入 IR 转换时可只摘掉协议那一条。

> 决策（2026-09-12）：软筛选**暂不实现**，先只统一能力词表（见 §5 M1.3）；本节建模保留，待确有多模型候选需求时再启用。

## 5. 落地路线（已定稿）

> 决策前提（2026-09-12）：项目以「自用稳定、长期积累真实数据」为终点，数据不得再随版本升级丢失；先收地基、再做降级；能力 / 上下文底线只统一词表，暂不做软筛选；性能先测量再决定。

### M1. 地基收口（四项独立，可分别提交；详细步骤见 `docs/superpowers/plans/2026-09-12-m1-foundation-hardening.md`）

1. **Schema 增量迁移框架**（对应 §7，最高优先：它保护此后所有真实数据）
   - `configure` 由「版本不符即 `reset()`」改为阶梯：`user_version == 0` 建库；`0 < v < 最新` 逐级迁移；`v > 最新` 拒绝启动并告警（不静默清库）。
   - 迁移定义集中为 `db/migrations.rs` 的 `[(version, sql)]` 阶梯；保留 `CREATE INDEX IF NOT EXISTS` 的幂等补建。
   - **不**引入无意义的占位版本：首个真实迁移由第 2 项（`route_targets` 去重 + 唯一索引）承担，顺带验证迁移机制。
   - 验收：构造旧版本库并灌入假数据，升级后数据不丢；`open_in_memory` 全绿；`request_logs` / `settings` 不动。
2. **`route_targets` 改为 upsert**（对应 §6）：`save_route` 按 `(route_id, upstream_model_id)` upsert、删除输入中移除的目标，使 target `id` 稳定 —— M2 的 attempt 记账与「日志引用履约 target」的前置。补一条「去重 + 唯一索引」迁移作为迁移框架的首个真实用例。
3. **能力词表后端权威化**：后端 const 定义（`vision` / `tools` / `reasoning`）+ 保存校验；前端 `providerModel.ts` 镜像并加一致性测试（对应 §6 词表无约束）。**不**实现软筛选。
4. **dev 与 release 数据库隔离**：dev 构建使用 `lumen-dev.db`、release 使用 `lumen.db`，避免调试 / 演示数据污染真实账本（`inject_demo` 会清空全部业务数据，而两者此前共用同一个 `app_data_dir()/lumen.db`）。

### M2. 同协议降级（自研、可测）

1. `resolve` 由 `LIMIT 1` 改为返回**有序候选**。
2. `forward` attempt 循环：仅连接失败 / 超时 / 5xx / 429 触发切换；4xx、鉴权失败、内容策略不切换（§3.1）。
3. **按 attempt 记账**：失败的尝试也写日志（`attempt_index` / 实际履约 target），守住「账不低报」红线，优先级高于一切可选功能（§3.3）。
4. 非流式先跑通，再流式 pre-first-byte；首字节后不降级（§3.2）。
5. 前端保存期对「无可用备用」只**告警**，不硬拒。
   - 验收：新增测试「首候选 500 → 次候选成功」，日志两条、金额与手工核对一致。

### M3. 跨协议转换（外部依赖 SDK，独立里程碑）

1. 推动 `llm-protocol` 补齐 G1 / G2 / G3（OpenAI 缓存用量、缓存边界、`decode_usage`）与 G5 / G6 / G7（SSE 编码、bytes 门面、流中错误编码）。
2. 网关接入 `StreamingConverter` / `decode_usage`，替换或并行自研 SSE 扫描。
3. 用量保真对齐：`cache_read_in_input` 与 `UsageSource`。
4. 放开协议锁定：`route.protocol` = 下游、`provider.protocol` = 上游，仅在接入转换后允许不一致。
5. 按 `requires_max_output_tokens` 等能力驱动 `ConversionPolicy`。

### M4. 性能与硬化（度量驱动）

1. 跑 `bench_overview` / `bench_logs` / `bench_key_usage`（Rich 场景），在 ~5 万 / 50 万 / 100 万行记录耗时与 `EXPLAIN QUERY PLAN`，据此决定是否实施 §8 的 rollup / 读连接池。
2. 评估 `useAnimatedMetric` 每次从 0 数起的观感成本。
3. 确认 M1 的迁移机制在真实数据上跨版本不丢。

> 节奏：M1 三项独立提交 → M2 一个专项 → M3 / M4 视精力穿插；每步保持 `cargo test` + `cargo clippy -- -D warnings` + `pnpm build` / `pnpm test` 全绿。

## 6. 相关技术债 / 前置

- 能力词表后端无约束（`Vec<String>`）。
- `save_route` 全量重建目标（`route_targets.id` 每次变化）；未来若日志需要引用 target，应改为按 `(route_id, upstream_model_id)` upsert。
- `docs/后端接口文档.md` 需随上述变更持续同步。

## 7. 开发期数据策略：Schema 变更即重建空库

- 现状：`db/mod.rs` 的 `SCHEMA_VERSION` 不符时走 `reset()`，`DROP_ALL` 包含 `request_logs` 与 `settings`。任何表结构改动都会清空全部流水与设置。
- 这是**发布前的有意识妥协**：字段与结构尚未定型，逐列迁移成本高、收益为零，且当前数据均为测试数据。
- 收口决定（2026-09-12）：因项目定为「自用稳定、长期积累真实数据」，已**提前**把增量迁移列为 M1 第一项（见 §5 M1.1），不再等到「发布前」。此后表结构变更一律走迁移阶梯，`request_logs` 与 `settings` 不得再随版本升级丢失；M1.1 落地前，仍沿用一个版本的清库窗口。

## 8. 性能优化方向（待基准验证，尚未实施）

背景：`request_logs` 的查询维度（时间 / virtual_key / 层 / status）已由覆盖索引承担，且 `with_db` 单连接串行。**拆事实表在当前负载下收益有限、反而增加写入成本**，不作为首选。按性价比排序：

1. **写入热路径**：每请求 1 次 INSERT + 1 次额度 SUM。可评估 `PRAGMA synchronous=NORMAL`（WAL 下安全）省 fsync；审视索引写放大（`idx_request_logs_alias`、`idx_request_logs_usage_source` 是否必要）。
2. **让规划器自选索引**：日志列表现用 `INDEXED BY` 硬钉 occurred 索引（`db/logs.rs`）。批量写入后跑 `ANALYZE` / `PRAGMA optimize`，可能让多数 hint 可撤。
3. **统计提速**：总览页真变慢时，加按 `(day, virtual_key_id, upstream_model_name)` 的 rollup 表（插入时增量 upsert），把总览从扫明细变成读几十行。代价是写入复杂度与跨期翻转的一致性。
4. **并行读取**：若要实现「多维度并行查询」，唯一有效手段是 WAL + 读连接池（多读连接），而非拆表；需处理 `SQLITE_BUSY`。
5. **不采用**：按月水平分表（跨期需 UNION、全局搜索要改造，15 万行/年远未到量级）；星型规范化（破坏账本的点时快照语义）。

**验证方式**：先跑现有基准 `bench_overview` / `bench_logs` / `bench_key_usage`（`#[ignore]`，`DemoScenario::Rich` 造 >2 万行），记录耗时与 `EXPLAIN QUERY PLAN`；再用 50 万 / 100 万行复跑看拐点，据此决定是否实施 3 / 4。
